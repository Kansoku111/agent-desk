# 次段階のGPT効率改善計画

状態: ステップ1の診断を実装。操作・仕様は[GPTキャッシュ診断](../gpt-cache-diagnostics.md)を参照。ステップ2以降と有料実験は未実施。実装開始前の検査基点: `1eff2f7` と既存の未コミット変更。

## 目標・最初の着手

代表的な実務課題で、Codex appと同等の成功条件・品質を維持し、完了する仕事あたりの消費を継続して下げる。工学上の目標は同一単価換算で20%減。これは達成済みの節約率でも、すべての課題・利用枠での保証でもない。

**最初に実装するのは送信前・生usageの最小観測だけ。** 既存テストとモックで制御・非漏洩を検証してから、回数と消費上限を決めた実モデルpilotへ進む。原因不明のままキャッシュ制御・履歴・推論設定を変更しない。

既存判断は[調査記録](../gpt-efficiency.md)を参照。モデル・プロバイダー・課金経路、保存済みeffort・文脈上限は変更しない。通常のツール/スキルを無断で外さず、境界・認証・承認・中断・ストリームの契約を維持する。

## 成功の測り方

- 一次指標: 同じ課題群に費やした総消費（失敗、再試行、要約、子を含む）と、完了数・成功率。完了しなかった安い試行を勝ちと扱わない。
- 記録: 未cache入力、cache read/write、出力（推論を二重加算しない）、モデル呼出数、要約、エラー、実行時間。0と未報告を区別する。
- 比較は対応する課題ごとの比率と中央値・ばらつきを示す。成功率・必須テストが悪化した変更は採用しない。小標本では一般的優位を宣伝しない。
- API単価換算とChatGPT利用枠は別。利用枠は同時利用を除ける時間帯で別途確認し、更新遅延・丸めや帰属が解消しなければ不明のまま残す。

## 1. 診断の追加（無償モックで開始可）

接続点は[siwc-request.js](../../server/siwc-request.js)の `withSiwc` にある最終 `siwcPayload` 適用後、認証ヘッダの内容には触れない送信境界。SSEは既存の `explainSiwcUsage` の解析時に書換前のusageを観測し、同ファイルの `requireCompleted` の終了検知と協調する。別readerや全応答の保持を追加しない。正規化前・SDKで0補完された後だけを観測して済ませない。

- 比較プロセスだけで明示的に有効化。通常時はOFFで、追加の本文シリアライズ・書込・外部通信をしない。UIや保存設定を増やさない。
- プロセス内で生成し保存しない秘密値によるHMACで、指示、ツール定義、入力要素、cache key、実効設定の同一性・先頭一致項目数・最初の差分位置を記録。本文、tool引数、encrypted_content、認証値や個人指示は保存しない。暗号化推論もdigestだけに含める。
- 同一HTTP試行の `response.completed` 等の生usageを対応付け、cached_tokensの正数・明示0・欠落・不正値を分ける。生input/outputとSDK後の計数が一致するか検査。失敗してusageが無ければ0とせず不明にする。
- ログ量を上限付きにし、診断の失敗で会話を失敗させない。認証、URL制限、retry、idle timeout、キャンセル、返却bytes/headersの意味を変えない。
- 検証は[SIWCテスト](../../test/siwc.test.js)と同じmock fetch/SSE形式を利用。chunk分割、追記だけの同一prefix、前方定義変更、設定変更、usage欠落/0、異常終了、診断OFFと書込失敗を固定し、既存の `siwc*.test.js` も通す。

合格条件: 診断OFFの送信内容・ストリームが不変、ONでも元の応答を失わず、生usageの有無と入力の変更箇所を判別でき、秘密値・本文がログへ出ない。過去の単発missの原因がこのモックで確定したとは扱わない。

## 2. 比較課題の固定と小さなpilot

短い修正、複数ファイルの修正、同じ会話を継続する長めの作業を用意する。意味のない長文paddingだけで実務効率を代表させない。品質判定はモデルから独立したテストで固定し、モデル自身による必須テストの完遂も条件に含める。

同じモデル/effort・初期ファイル・依頼・個人設定除外・実効権限を生ログで確認し、両者の通常のハーネス差は残す。試行順を交互にし、cold/warm状態を記録して結果を選別しない。各課題3ペア程度はpilotにすぎず、予算を決めて小さく開始する。実験準備は無償で行い、実呼出は回数・トークン上限・中止条件を明示してから。既定の実モデル検証はAGENTS.mdどおりLuna/lowで、別モデル/effortが必要なら明示する。

実行コア/CLIでの反復は切り分け用。最終的に「Codex appより少ない」と主張する前に、実際の両アプリでも同条件を確認する。初期化不備を正当な製品差とせず、無効試行の消費も別記する。個人指示除外のためにWindows実行基盤まで外す失敗を再発させない。

## 3. 効果のある修正を1つずつ採用

1. 生usageが保存時に失われるなら、その変換だけ直す。これは実消費削減とは別の計測修正。
2. 既存入力の前方やcache関連設定が変わるなら、その具体的な経路だけ直す。後着ツール・権限・設定変更の意味を壊さず、同じfixtureで再比較する。
3. 入力が安定しても上流missなら、根拠なく制御項目を増やさない。長い会話の不要な往復、同じファイル/結果の再取得、無駄な補助推論など、記録された回数・量の大きいものへ移る。
4. 過去の出力を削る、早期に要約する、fresh子へ分ける変更は、取得し直し・要約費用を含む全体コストと品質を比較してから採用する。単に文脈上限を下げて達成扱いにしない。

合格条件: 同じ品質で代表課題群の総消費が下がり、特定の1回のhit/missだけで結論が逆転しない。下がらなければ戻し、新しい理由がない限り同じ検証を繰り返さない。

## 4. 利用枠の差が残る場合の設計判断

送信量と品質で同等以下でも実際の利用枠で負けるなら、SIWCとCodex側の経路・計上条件を分離して考える。非公開の係数をプロンプトだけで覆せるとは約束しない。必要ならGPT向けにCodex実行コアを使う明示的な選択肢を別設計として評価する。現行のDSH機能・権限・認証・課金経路を勝手に置換しない。この分岐には別途の設計確認とユーザーへの説明が必要。

## 実装引継ぎ

ステップ1の観測とmock試験を実装済み。この文書と最新の差分・検証結果を照合し、次の比較へ進む前に予算と試行の条件を確定する。既存の未コミット変更を保護し、結果を記録して自分の変更だけコミットする。根拠が不足する最適化や予算未設定の有料試行へ進まない。対処しても同じ失敗に新しい証拠が得られなければ、その工程を設計へ戻し、他の独立した検証は続ける。
