# 回答リンクのExplorer表示・前面化

## 2026-11-10 / 連続操作と前面化の見直し

- 同じフォルダーの4ファイルを同時に表示すると、Explorerが一つのビューを再利用し、別の要求が選択を上書きして3件がタイムアウトしました。Windowsの `file.open` はパス解決から表示確認までを受け付け順に処理します。失敗した要求の次も続行します。
- フォルダーを開く操作では、選択数0の `SHOpenFolderAndSelectItems` が親フォルダーに移動していました。フォルダー自体の表示とドライブのルートには `explore` 動詞を使います。親の中で選択する操作では、従来どおり対象をPIDLで渡します。[Windows Shellの選択API](https://learn.microsoft.com/ja-jp/windows/win32/api/shlobj_core/nf-shlobj_core-shopenfolderandselectitems)
- 対象の表示・選択が確認できた後、最小化されていれば復元を待ってから前面化を試します。最小化されたウィンドウのハンドルをWindowsが前面として返すことがあるため、両方の状態を確認します。前面化できない場合はタスクバーを点滅させ、画面から案内します。擬似Alt入力は他のアプリにも作用するため廃止しました。RPCには必要な場合のみ `background: true` を追加するので、既存のクライアントも表示結果を受け取れます。[Windowsの前面化制限](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)
- 上記の変更後も実機では毎回 `background` になり、前面に出ませんでした。ヘルパーはサーバーの子プロセスで前面プロセスではないため、`SetForegroundWindow` が前面ロックで拒否されていました。前面化の直前だけ、現在の前面ウィンドウ（クリックしたAgent Desk）のスレッドに `AttachThreadInput` で入力キューを接続して実行します。擬似Alt入力と違い、他のアプリへの入力は発生しません。実機で、背面の既存ウィンドウの再利用、最小化からの復元、フォルダーを開く操作のいずれも前面化を確認しました。拒否された場合のタスクバー点滅と案内は残しています。
- それでも、Explorer本体ではなくシェル拡張（Folder Size）の小さな窓だけが前に出ることがありました。ShellWindowsには非表示（`WS_VISIBLE` なし）の `CabinetWClass` が残っており、Explorerがそれを再利用して選択していました。表示される前に一致と判定して前面化していたため、所有されたポップアップだけが前に出ていました。非表示ウィンドウの発生経路は再現できていません（通常の閉じる操作では残りません）。一致したウィンドウは表示中のものを優先し、非表示しかなければ表示してから前面化します。前面判定も、表示中のウィンドウに限ります。実機で、非表示に戻したウィンドウへの表示が表示・前面化まで成功することを確認しました。
- パス解決では、末尾のアポストロフィなどがファイル名の一部である場合を先に試します。引用符や句読点を外す従来の解釈は、入力どおりの項目が見つからない場合に使います。

回帰テストは `node --test test/file-open.test.js test/file-refs.test.js` です。要求の順序と失敗後の続行、フォルダー・選択の呼び分け、背景表示と実際の表示失敗の区別、末尾にアポストロフィがあるパスを確認します。実機でも、一時ホームのAgent Deskにフォルダーを開く要求と4件の選択要求を連続で送り、順序と最後の選択を確認しました。最小化した同じウィンドウの復元と選択も確認しました。

## 2026-10-26 / 初回修正

2026-10-26 / Windows。最初の依頼では調査だけを行い、その後の修正依頼を受けて、Explorer表示と起動結果の通知を修正しました。

## 修正内容

- `server/open-front.ps1` の `explorer.exe /select,...` 起動を、Windows標準の `SHOpenFolderAndSelectItems` に変更しました。フォルダーと選択対象をPIDLで渡すため、日本語・空白・カンマ・引用符・`&`・角括弧をコマンド文字列として解釈しません。
- ウィンドウの新旧ではなく、Shell.Applicationのフォルダービューと選択された項目が要求に一致するExplorerを特定します。既存ウィンドウが再利用されても、最小化を解除して前面化します。関係のない新規ウィンドウを前面化する処理は削除しました。
- Explorerの対象ビュー・選択と実際の前面HWNDを確認してから成功とします。表示待ちや前面化が成功しなければ終了コード1とエラーを返します。Windowsの前面化制限を無条件に解除するものではなく、拒否された場合はその旨を通知します。
- `server/system.js` はWindowsのSTA PowerShellヘルパーを待ち、標準エラー・終了コード・15秒のタイムアウトを日本語のエラーにして返します。パスは専用環境変数で渡します。macOS/Linuxの既存の非同期起動方法は変更していません。
- `server/rpc-handlers-workspaces.js` の `file.open` も完了を待つため、失敗は既存の画面のエラー通知へ届きます。
- 通常ファイルの「開く」は既定の関連付けから起動し、起動エラーを返します。実行ファイル・スクリプトは引き続き直接実行せずExplorer表示へ切り替えます。フォルダーの「開く」はそのフォルダーを表示し、「エクスプローラーで表示」は親の中で選択します。ドライブのルートはそのまま開きます。

## 原因と確認結果

以前の実装には次の2つの問題がありました。

1. 新しくできたHWNDだけを前面化対象にしており、既存Explorerを再利用した場合を扱えませんでした。
2. PowerShellのエラーを抑制し、サーバー側でも起動結果を捨てて成功扱いにしていました。旧ヘルパーでは、起動だけを診断用に失敗させても終了コード0になることを確認しています。

修正後はWindows実機で次を確認しました。

- 実際の `file.open` ハンドラー → Nodeの起動処理 → PowerShell → Windows APIの経路でREADMEを選択し、完了後の前面HWNDが対象Explorerと一致すること。
- 同じExplorerを最小化後、別ファイルへの表示で**同じHWND**を再利用し、最小化解除・新しい選択・前面化がすべて成功すること。
- 日本語・空白・`&`・角括弧・引用符を含む一時フォルダーとファイルで、対象の選択と既存ウィンドウの復元が成功すること。
- フォルダー自体を開く操作と、親の中でフォルダーを選択する操作。

調査で開いたウィンドウだけをHWND・場所で照合して閉じ、一時フォルダーも削除しています。ユーザーの会話や作業ファイルは変更していません。
