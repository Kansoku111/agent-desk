# 回答リンクの右クリック操作の調査

2026-10-26 / Windows。依頼どおり、リンク関連の本番コードは変更していません。

## 結論

通常のローカルリンクでは、右クリックの「開く」「エクスプローラーで表示」から正しい `file.open` 要求が出ることを確認しました。正規化済みの実在する Windows パスで既存の起動スクリプトを実行すると、Explorer の対象フォルダーが開きました。したがって、この操作が常に失敗する状態は再現していません。

一方、次の問題は確認できています。今回失敗した具体的なリンクが未提示のため、どれが実際の症状を起こしたかは断定できません。

## 確認できた問題

### 1. Windows の起動失敗を利用者に返せない

- `server/rpc-handlers-workspaces.js:97-104` はファイルの実在確認後に `openFile` を呼び、起動完了を待たず成功結果を返します。
- `server/system.js:100-124` は PowerShell を `detached: true, stdio: 'ignore'` で起動し、終了コード・標準エラーを受け取りません。
- `server/open-front.ps1:8,50-54` は `SilentlyContinue` のため、通常の起動エラーを抑制します。
- 実際のスクリプトの `Start-Process` だけを診断用の失敗関数に差し替えたところ、内部にエラーが残っているのに `ScriptSucceeded=True`、PowerShell の終了コードも `0` でした。ファイルやアプリは開いていません。

このため、Windows 側で失敗したときにメニューだけが閉じ、エラーも出ない症状になります。起動失敗そのものの理由（対象リンク、関連付け、Windows 側の状態など）は今回の情報だけでは特定できません。

### 2. 一部の行番号付きリンクが表示段階で無効になる

`web/src/link-transform.ts:13-15` はドライブレターと file URL 以外を react-markdown の既定フィルターへ渡します。

| Markdown のリンク先 | 変換後 |
| --- | --- |
| `README.md:42` | 空文字（無効） |
| `src/app.ts:42` | そのまま |
| `README.md#L42` | そのまま |
| `F:/Agent-Desk-DSH/README.md:42` | そのまま |

フォルダー区切りより前にコロンが現れる `README.md:42` は、URL のスキームと判定されて除去されます。ブラウザーの実際の Markdown 表示でも、このリンクだけ `FileRef` にならず、専用の右クリックメニューを使えないことを確認しました。バッククォートのインラインコード表記は別経路です。

### 3. 前面化の対象が「新しくできたウィンドウ」だけ

`server/open-front.ps1:48,56-63` は起動前後の HWND の差だけで対象ウィンドウを探します。既存ウィンドウや既存タブが再利用された場合は前面化されない構造です。これはコード上の制約であり、今回の実測では新しい Explorer ウィンドウが作られたため、この条件での症状は再現していません。

## 確認範囲と未解決事項

- UI は実際の `Markdown / FileRef / FileMenuHost` をブラウザーで動かし、RPC だけをモックして開く・表示の要求内容を確認しました。ユーザーの会話データは変更していません。
- Explorer はリポジトリの README を対象に既存スクリプトを実行しました。調査で開いたウィンドウだけを HWND と場所の両方で照合して閉じています。
- 既存の `test/file-refs.test.js`、`test/link-transform.test.js`、`test/system-open.test.js` は全体テストで成功しています。ただし `system-open` のテスト対象は主に別のターミナル起動経路で、上記のファイル起動失敗を検出できません。
- 実際に失敗するリンク先と、「メニューが出ない／選んでも無反応／別の場所が開く」のどれかが分かれば、表示前の変換・パス解決・Windows の起動／前面化のどこで止まるかを確定できます。
