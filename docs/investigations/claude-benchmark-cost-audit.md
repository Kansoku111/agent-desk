# 新カード実装ベンチのClaude換算額調査

調査日: 2026-11-03。[当初の横断調査](claude-equivalent-cost-audit.md)に対し、提示されたベンチの対象担当を特定して追加確認した記録。アプリ・ベンチの保存結果は変更していない。

修正状況（2026-11-03）: `ClaudeRunner` は応答ID別にストリームの累積出力を反映するよう修正し、重複・遅延ブロック・停止・子の混入・不正値・長文段階の回帰テストを追加した。保存済みのベンチ結果と使用量は未変更。以下の数値は修正前の記録であり、現行仕様は[使用量の表示](../usage.md)を参照する。

## 結論

このベンチではClaude換算額の過大計上は確認せず、逆に**非対話ClaudeRunnerの出力使用量の取得漏れ**を確認した。時間あたりの金額が高くなる主因は、多数のモデル呼出しによる長い履歴のキャッシュ読込・作成と、Haiku 5.5の長文料金段階だった。

## 元資料と検証範囲

ベンチ作業フォルダーの `新カード_最終比較.json`・`新カード_全方式_作業量.json` を確認し、開始時刻から3つのClaude担当（Sonnet単独、Sonnet計画、Haiku実装）を対応付けた。保存済みターン使用量とClaude Codeの元会話ログを比較し、元ログの応答ID別に最終使用量を読み、公式料金の独立した式で再計算した。モデルの実呼出しはしていない。

| 方式 | 比較表の算定済み額 | 元ログから再計算した算定済み額 |
| --- | ---: | ---: |
| Sonnet high 単独 | $4.3835803 | $5.1006003 |
| Terra計画 → Haiku実装 | $2.04224518 | $2.42534718 |
| Sonnet計画 → Luna実装 | $1.55829561 | $1.74894561 |

全行で合成エラー応答の未算定表示は残るため、再計算額も厳密な全額や実請求額ではなく下限。複合行の非Claudeステージは保存済み金額を据え置いた。親・採点・画像生成費用を加算したものではない。

## 高くなる内訳

### Sonnet単独

- 算定可能なモデル応答119回。キャッシュ読込21,471,263、作成554,332トークン。作成は全量1時間TTL。
- 元ログの出力73,567に対し、担当の保存済み出力は2ターン合計1,865。入力・キャッシュ量は一致。
- 独立計算: 未キャッシュ入力 $0.000476 ＋ 出力 $0.73567 ＋ キャッシュ読込 $2.1471263 ＋ 1時間作成 $2.217328 = **$5.1006003**。
- キャッシュ関連が約86%。26分25秒という時間ではなく、各呼出しで消費したトークンに対して料金が発生する。利用上限による待機は約5時間44分で、1時間TTLより長い。再開ターンでは292,189トークンの作成が記録されており、待機を稼働時間から除いても、その再作成料金は残る。

比較対象のSol単独は50応答・キャッシュ読込5,900,928・作成0トークン（保存記録）。読込単価はSonnet 5.5と同じ $0.10 / 100万であり、Sonnetの読込量は約3.64倍。単価だけでなく、呼出回数と履歴量が異なる。トークナイザー・ハーネスも異なるため、差をモデル単体の効率へすべて帰属させない。

### Haiku実装

- 算定可能なモデル応答178回。キャッシュ読込32,969,636、作成489,242トークン。作成は全量1時間TTL。
- **131応答がキャッシュを含む入力100,000トークン超**。この段階では入力・出力・キャッシュの単価が低入力段階の5倍になる。
- 元ログの出力185,163に対し、保存済み出力は1,455。
- 独立計算: 未キャッシュ入力 $0.0001404 ＋ 出力 $0.3860415 ＋ 読込 $1.53002568 ＋ 1時間作成 $0.3484596 = **$2.26466718**。別担当のTerra計画 $0.16068 を加えると **$2.42534718**。
- `xhigh` という設定名に固定の料金倍率を掛けた結果ではない。長文段階と実トークン量から計算した値。

## 取得漏れの箇所と再現

調査時点の `server/claude-runner.js:454–469` は `stream_event` を速度計測にだけ使い、`message_delta.usage.output_tokens` を保存使用量に反映しない。`assistant.message.usage` だけを応答IDごとに保存し、応答が一つでもあると最終 `result` の使用量も採用しない（491–498行）。

初期使用量のままのassistantイベントが来る経路では、最終出力数を取り逃す。実際に上記3担当では、元ログの最終出力と保存済み出力に差があり、料金差は出力の取得漏れで説明できた。Sonnet計画は保存173に対して元ログ19,238出力で、差額は $0.19065。

既存テストのfakeSpawnと同様のモックプロセスで、実モデルを呼ばず次を確認した。

- Haiku 5.5 / low、入力10。assistantイベントで出力1、続く `message_delta` で最終出力1,000を通知。
- 正しくは出力1,000・$0.000501。
- 修正前Runnerの記録は出力1・$0.0000015で、`priced: 1, unpriced: 0` のまま。

したがって、画像の「≥」はこの取得漏れを完全に検出した印ではない。既存の未算定1件は別の合成応答であり、算定済み応答自身にも取得漏れがある。

## 修正状況と残る課題

- 修正済み: 最終usageを応答IDへ結び付け、累積値は加算せず置換する。初回の単価・TTL・速度を維持し、遅延ブロックや子エージェントの使用量が結果を壊さない回帰テストを追加した。部分イベントによる本文追加や速度計測の処理は変更していない。
- 過去の非対話担当には応答別の使用量・単価スナップショットが保存されていない。現在単価で全履歴を一括上書きせず、復元可能な対象と算定単価を確認して補正方針を決める。
- 修正済み: 当初発見した同梱Sonnet 5.5の読込単価を $0.20 から $0.10 へ変更した。ただし、このベンチの読込は正しい $0.10 で計算されており、今回の高額の説明にはならない。
- モデルの選び方と並んで、ツール往復・長い出力・コンテキストの肥大化を比較する必要がある。この1試行だけでClaude全般の性能や費用対効果を確定しない。
