# 通常タスクの「子に委託」「独立レビュー」プリセット調査

## 結論と開始境界

**実現可能。常設の委託MCPを追加せず、Agent Deskのサーバーが必要なときだけ既存のモデル実行機構を起動する方式を推奨する。** 通常タスクをTM/ecoに変換せず、会話と親モデルをそのまま残す。

- **子に委託**：通常タスクの現在のモデルが、合意済みの方針を短い実装契約にまとめる。設定済みの子モデルを新しい会話で起動し、実装・検証まで担当させる。
- **独立レビュー**：設定済みの別モデルを新しい会話で起動する。要件と実際の差分からレビューし、見つけた問題を同じモデルが修正・検証まで完了する。**指摘の報告だけで終える機能ではない。**
- 親子間の制御はUI → 既存の認証済みRPC → アプリ内の管理処理で行う。モデルに起動権限や内部APIの認証情報を渡さない。
- 操作していない通常タスクへの追加ツール定義・常設プロンプト・モデル呼び出しはゼロにする。既存のブラウザ等のMCPや通常のサブエージェント設定を勝手に変更する意味ではない。

今回の依頼は調査のみ。製品コードは変更しない。本書は設計提案であり、実装済みの使用説明ではない。将来実装を依頼された場合は「実装手順」のP0から開始できる。**親の出力回収を実測するP0を通るまで、自動の子起動を有効にしない。**

調査基準：HEAD `15d4025`（Show AB and eco settings beside TM in Settings → Agent teams）と調査時の作業ツリー。端末ダイアログ等の未コミット変更が既にあり、それらには手を加えない。日付・依存バージョンだけで判断せず、着手時に差分と以下の参照先を確認する。

## 採用する動作

### UIと設定

1. 「設定 → モデル」に「タスクのプリセット」を置き、「子に委託」「独立レビュー」のモデルと推論レベルだけを並べる。[WorkflowModelField.tsx](../../web/src/components/WorkflowModelField.tsx) と [workflow-effort.js](../../shared/workflow-effort.js) の選択・解決規則を使う。
2. アプリ側の設定に任意の `taskPresets` を追加する。各役割は `{ model: null, effort: null }` を初期値とし、未設定時は実行せず設定へ誘導する。モデルIDは既存の形式（`claude:...` またはカタログのvalue）を使う。系列別サブエージェント・TM・AB・ecoの設定は移し替えない。推論未指定は既存workflowと同じ新規開始時の解決規則を使い、実効値を表示・記録する。
3. 通常dshタスクと通常Claude Code端末の「開く」に、区切りを入れて2項目を追加する。チームの親子、eco、AB、作業フォルダーだけの画面には追加しない。`OpenInMenu` へ任意のtask参照を渡し、未指定なら今までどおりとする。リモートでも同じ認証済みRPCを使う。
4. 選択後の小さな開始画面では、担当モデル・実効権限・任意の追加指示を表示する。独立レビューには対象範囲を1行で表示し、必要なときだけ変更できるようにする。長い説明文や「計画型／プロンプト型」などの追加プリセットは置かない。開始操作が書き込みと選択した課金経路への同意になる。
5. 独立レビューには「指摘箇所を修正します」という短い文を開始ボタン付近に一度表示し、報告専用と誤認させない。モデル・プロバイダー・認証経路の変更は隠さない。
6. 実行結果は元タスクに紐付くカードと詳細ビューで見せる。担当、段階、変更、検証、停止／未完了が分かる構成にする。結果全文・差分はアプリデータに保存し、親へ戻すためだけのモデル呼び出しは行わない。利用者が必要なときだけ「結果を渡す」で短い結果と資料参照を親へ送る。

独立レビューでは、記録済みの元の実装モデルと同じモデルを選んでいる場合は別モデルの選び直しを求める。元の実装モデルが不明な旧データではその旨を表示し、別モデルであることを保証したとは表現しない。別モデルへ黙って切り替えるfallbackにはしない。

既存の `subagentsEnabled` はモデルが自律的に使う委託ツールのスイッチとして維持する。オフでも、人が明示するこのプリセットは利用できる。プリセット側の子には、同設定にかかわらず孫委託を載せない。

### 子に委託：長い計画ではなく、短い実装契約

```text
ユーザーが開始
  → 現在の親セッション：合意内容を実装契約へ整形
  → アプリ：出力検証・変更前の記録
  → 設定済みの子：必要なコード確認 → 実装 → 検証・手直し
  → アプリ：選択済み検証・差分記録 → 元タスクへ結果表示
```

「計画を作るか、指示プロンプトか」は二者択一にしない。親が既に把握している内容を、**目的・範囲／非対象・合意済み方針・受け入れ条件・検証・重要な未解決点・必要な参照**にまとめる。手順が必要な仕事だけ短く添える。計画専用モデルを追加したり、決まった設計をもう一度調査し直したりしない。

親には契約の作成だけを依頼し、このターンで実装・子起動・shellからの内部API操作をしないよう指示する。親モデル・推論レベル・通常のMCP一覧は変えない。このため親の実装禁止はプロンプト上の役割指定であり、新しいread-only sandboxを保証するものではない。準備前後のソース指紋が変わった場合は子を起動せず要確認にし、変更を勝手に巻き戻さない。契約作成のためのモデル呼び出しは原則1ターンだが、通常のエージェントと同様、内部で複数のモデルリクエストになる可能性はある。

実装を左右する不明点がある場合は `needs_input` と質問を返し、子を自動起動しない。単なるコード確認や局所的実装詳細は子の裁量に残す。合意済み条件を文字数上限の都合で削らず、長い根拠は許可された資料参照に分ける。

### 独立レビュー：別の会話で調べ、同じ担当が修正・検証する

```text
要件・受け入れ条件 ＋ アプリが確定した対象差分・現在のコード
  → 新しいレビュー修正セッション
  → 独立に問題を探す → 問題の原因と範囲を確定
  → 指摘箇所を修正 → 関連テスト・必要な動作確認
  → アプリの検証 → 必要なら同じ担当で修正を継続
  → 修正完了／問題なし／具体的理由付き未完了を表示
```

- 最初から書き込み可能な実行にする。報告専用のread-onlyセッションを終えてから、もう一人へ修正を委託する構成にはしない。レビュー→修正で会話を作り直す必要もない。
- 初期コンテキストに親の推論過程、実装者の完了宣言、既存レビューの結論を渡さない。目的・ユーザー要件・受け入れ条件・実際の差分と、アプリが取得したコマンド結果を渡す。実装者が残したREADMEやコメントまで見えなくする仕組みではなく、認知的独立性の保証ではない。
- この機能で委託した実装には保存した契約を使い、原則として親を追加呼び出ししない。通常タスクから直接レビューするときだけ、親に結論を含まない要件ブリーフを1回作らせる。原文の該当リクエストを参照として残し、要約の脱落を確認できるようにする。
- レビュー担当は対象の不具合・回帰・要件違反を修正する。新機能追加、無関係な整形、好みだけのリファクタリング、検査を弱める修正には広げない。必要な関連ファイルと回帰テストの変更は許す。重大な仕様選択や権限外の変更は勝手に決めず未完了として戻す。
- 問題がなければ変更ゼロで終了してよい。ただし確認箇所と未確認点を報告する。問題を見つけたのに修正可能なものを放置して「レビュー完了」としない。
- 最終出力は、各指摘の根拠、修正内容または対応不要の根拠、検証結果、未解決項目とblockerを機械的に読める形でも残す。アプリは形式と状態整合を検査し、修正可能な未対応指摘がある報告だけの終了には、同じ担当へ継続指示する。モデルが自己申告した内容の正しさまでは保証できない。
- 検証で範囲内の失敗が判明した場合も同じ担当へログを返す。成功条件を緩めたり、親や別レビュワーを繰り返し呼ばない。新しい根拠が得られない同一失敗の反復、環境・認証・課金・権限の問題、範囲外の修正が必要な場合は、具体的理由付きの未完了にする。無限再試行で「完了まで」を実現しようとしない。
- 検証成功だけを正しさの証明としない。UI等に必要な確認ができなければ未確認を残す。同じレビュワーによる最終修正は、**さらに別のモデルによる再レビュー済みではない**。自動でレビュー担当を増やさない。

### レビュー対象と2つの基準点

指摘すべき実装差分の基準 `reviewBase` と、レビュワーが何を直したかの基準 `fixBaseline` を分ける。どちらも可能な限りアプリが内容を記録する。

| 元の作業 | `reviewBase` の選択 |
| --- | --- |
| このプリセットによる委託 | 委託実装の開始前スナップショット。子がコミットしていても内容差を取得する。 |
| 通常dshタスク | 変更がある直近の完了ターンのbeforeを候補にする。開始画面に対象リクエストを示す。複数ターンをまとめる場合は開始リクエストを選べるようにする。契約作成ターンを実装開始点と取り違えない。 |
| 通常Claude Code端末、旧タスク、チェックポイントが無効／欠落 | 基準を推測せず、利用者がGitの基準コミット、または「現在の未コミット変更」を選ぶ。非Gitで基準がない場合は対象ファイルと要件を明示するファイルレビューとし、過去との差分は不明と表示する。 |

Gitの基準コミット指定は、その確定SHAから現在の作業内容までを対象にする。未コミット変更も含むことを表示する。「現在の未コミット変更」はHEADからの内容差と未追跡ファイルを含める。HEADがない場合はこの選択を利用不可にする。対象のない空diffを「レビュー成功」にしない。**`git diff HEAD` だけでは既にコミット済みの実装を見落とす。**

基準refは引数配列で解決・検証し、shellへ文字列連結しない。Git除外・50MiB超・バイナリ等の未取得対象は既存チェックポイントと同様に明示する。差分を取得できない状態と変更なしを分ける。Git refからの差分取得は既存の `reviewDiff` だけでは完結しないため、実装時に専用の取得処理とテストを追加する。

`fixBaseline` はレビュー担当を起動する直前の現在の内容。ユーザーの既存未コミット変更を消さず、レビュワーの変更を別差分として保存する。コードレビュー範囲と修正後の実状態は、外部エディターからも変わり得るため、アプリの指紋比較で変化を検知したら古い結果として扱う。変更元の完全な識別やOSレベルの同時編集禁止は保証しない。

## MCPを追加しない実行方式

### 親からの受け渡し

現在の両ランタイムで共通に使える最小案は、アプリが一度だけ送った依頼への**最終assistant回答のJSONブロック**を取り出す方式。常設ツールや独自CLIをモデルに覚えさせる必要がない。ファイルへ契約を書かせる案は、作業ツリー汚染や親のread-only権限、アプリデータへの書き込み権限に依存するため採用しない。

以下は設計上の追加プロトコルであり、現時点の既存APIではない。

- 開始RPCでrun ID、request ID、source task/session、source turn、現在の設定のスナップショットを保存する。クライアント再送は同じrequest IDに対して同じrunを返す。別payloadでのID再利用は拒否する。
- 親への指示にはrunに対応する一度限りの識別子、固定schema版、必須項目、上限を含める。モデルは `{ version, requestId, kind, status, brief, questions }` を指定のJSONブロックで返す。`kind` は委託／レビューの開始記録と一致させ、`status` は `ready` または `needs_input`。`ready` の `brief` と `needs_input` の質問は必須とし、`brief` の項目は前述の実装契約／要件ブリーフに従う。
- 解析対象は、開始後に送信を確認した**該当ユーザー入力に対応する、正常完了ターンの最終assistantテキスト**のみ。思考・ツール出力・ユーザー原文・別ターン・会話全体の正規表現検索から実行を起こさない。
- 型・長さ・件数・許可フィールド・実行種別・sourceとの一致・既消費状態を検証する。JSONはデータとして扱い、コード評価しない。識別子は認証情報ではなく誤対応防止であり、UIによる開始記録がなければ何も起動しない。
- 親の出力にモデル・権限・任意の読取パスや実行コマンドを決めさせない。参照ファイルはサーバーで対象workspaceと明示的に許可された資料へ制限する。検証は選択済みの登録IDを使用し、JSONに書かれた任意shellをアプリが実行しない。
- 形式不正や出力欠落は子を起動せず、要確認として回答を表示する。自動修復用モデルを常設せず、人が再生成または内容確認して再開できるようにする。二重完了イベントでも子を二重に起動しない。
- dshは `send` の受理したturn IDを保持する。Claude Code端末は送信前の会話位置、入力の識別子、対応する新規ターンを照合する。Stop hookが先に届く、同じhookが重複する、会話ファイル未反映、割り込みで終了したケースをP0で検証する。曖昧なら自動起動せず要確認へ進める。

### 起動・権限・ツール

薄いプリセット専用管理処理を追加し、dshは `ThreadManager`、Claude Codeは `ClaudeRunner` の起動・再開・完了通知を利用する。AB/TMのIDや状態に偽装せず、任意のプリセット所有情報を保存する。新しい汎用ワークフローエンジンや外部MCPサーバーは作らない。

- 実装担当・レビュー修正担当とも新規の会話から始め、子の手直しは同じ会話を再開する。会話全文forkはしない。workspaceのAGENTS等と有効なカスタム指示は引き続き適用する。添付画像等は必要かつ選択先が対応するものだけ明示的に渡し、無関係な添付や全履歴は渡さない。
- dshの書き込み権限は `workspace-write` を既定にし、full accessは利用者が開始画面で明示した場合だけ。親がread-onlyでも親を昇格せず、子の権限を別に表示する。CLI経路は既存AB同様の `bypassPermissions` を使う場合にfull accessを必ず明示し、同意なしに開始しない。既存ABの「常にfull access」を通常タスクから黙って継承しない。
- 通常の承認待ちを見えないまま残さない。実行に利用者の判断が必要なら要確認として見せる。権限不足を迂回したり、自動昇格・ACL変更を指示しない。
- 子の実行プロファイルから再委託、workflow、goal、自動設定変更を除外する。実装・レビュー修正に必要なread/edit/write/shell/検証用ツールは残す。レビュー担当をread-only allowlistに入れない。
- 追加MCPは既定では付けない。UI確認等で必要なら開始画面から既存のブラウザツールだけを明示的に有効化できるようにする。Claude Codeは `--strict-mcp-config` と `--no-chrome` を基礎に、許可したツールだけを構成し、ユーザーグローバルMCPを暗黙に継承しない。モデルの組み込み指示も含めて実際の定義をテストする。
- API、ChatGPTサブスクリプション、Claude Codeの経路を明示し、利用不可モデルや非対応推論値は開始前に拒否する。別モデルへの自動fallbackは追加しない。Claude Codeのauth preflightと認証経路の同意は [claude-auth.js](../../server/claude-auth.js) の既存方式を使う。

### 排他・停止・保存

プリセットはどちらもwriter。親が作業中、承認待ち、裏の子やコマンドが動いているときには始めない。子の起動前から最終検証まで同一・上位・配下workspaceのwriter／復元と排他にし、親自身の追加入力も作業開始させない。開始とロック獲得の間に別作業が割り込まないようにする。

既存のガードへ今回のrunを加える最小変更とし、ecoの全ルールの一般化や無関係な競合修正は混ぜない。ただし新runとの競合は、開始順によらずthread・端末送信／再開／入力・復元・TM/eco・ABの両方向で同じ重複パス判定を使う。読み取り専用の並行閲覧は止めない。端末のプロトコル応答や停止操作まで遮断しない。

独立レビューの書き込み開始前には、必要な要件ブリーフ作成を終える。ブリーフ作成からwriter起動までをrunの予約として扱い、その間に対象が変化したら基準を再提示する。予約中は対応する親のブリーフ作成ターンだけを通し、worker稼働中は親の明示入力・自動goal roundの両方を待機させる。既存の `setGoalWaiting` 等のスケジューリング制御を参照し、保存済みgoalの内容・phase・残り回数を勝手に書き換えない。動いている親を強制停止して起動する動作にはしない。

保存先はアプリhome配下の `task-presets/`（提案）。設定自体は既存settingsに置く。runにはsource、役割、実効モデル／推論／権限／ツール、契約、2つの基準点、担当セッションID、段階、検証、最終結果を保持する。原実装差分とレビュワーの修正差分は別資料とし、大きい本文・ログは必要時だけ読む。使用量が取得できた分だけ集計し、未取得をゼロ扱いにしない。トークン、cache read/write、モデル呼び出し回数を親の契約作成と担当実行に分け、親の累計と二重計上しない。

段階は `preparing → running → verifying → completed / needs-attention / stopped` を基本にし、担当の進行としてreviewing/fixingを表示できるようにする。モデルの正常終了と作業完了は別。必須検証の失敗／未実行、未対応指摘、取得不能・古い証拠、未完了のバックグラウンド書き込みをcompletedにしない。選択されたコマンド検証がない場合は明示的にunverifiedとし、それだけで未確認の受け入れ条件を合格にしない。

停止は担当とアプリ検証を止め、遅れて到着した完了イベントで次工程を始めない。再起動中のrunは中断として復元し、明示的な再開なしに課金実行しない。既存の設定・保存済み通常タスクにはoptional項目を追加するだけで、旧データはプリセット設定なし／runなしとして扱う。source削除時は進行中runを止め、保持済み結果は元タスクがないことを示して参照可能にし、無関係なセッションを削除しない。

## トークン効率の評価

最も効くのは「MCPという通信形式を使わない」こと自体より、**呼び出さない通常ターンへのツール定義と説明の追加、子への全文転送、親の不要な再起動、別モデル間の重複調査を避けること**。ローカルプロセスが起動しているだけでモデルの入力トークンが発生するわけではない。

| 方式 | 今回の判断 |
| --- | --- |
| 通常タスクをTM/ecoに変換 | 常設の親向けツール・指示と進行管理が付く。今回の単発利用には不採用。 |
| クリック時だけMCPを追加して後で削除 | 実現余地はあるが、セッション再設定・ツールprefix変更・両ランタイムの扱いが増える。起動制御がアプリにある以上は不要。 |
| skill/CLIを毎回案内してモデルに起動させる | 常設説明は減らせてもCLI権限・内部認証・出力回収が別途必要。既存のアプリ起動経路があるため不採用。 |
| UI起点のアプリ管理run | 未使用時の追加モデルコンテキストが不要。親の短い契約と担当1セッションに絞れるため採用。 |

通常相談時の追加費用は発生させない。委託時には親の既存文脈を含む契約作成と子の実装、直接レビュー時には要件ブリーフ作成とレビュー修正が必要になる。契約作成後の依頼／回答も親の会話履歴には残り、後続ターンでの入力トークンが完全にゼロになるわけではない。

親のツール一覧やsystem promptを切り替えず、短い指示を既存履歴の末尾に足す方がprefixを維持しやすい。ただしcache hitや節約率は保証しない。[OpenAIのPrompt caching](https://developers.openai.com/api/docs/guides/prompt-caching.md) はレンダリング後のprefix一致を条件とし、セッションの維持だけではhitを保証しない。[AnthropicのPrompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching.md) もtools → system → messagesのprefixを扱う。APIの記述からChatGPT／Claude Codeの利用枠減少率まで推定しない。

未使用タスクのツール定義が不変であること、子へ履歴全文を渡していないこと、親の完了通知による自動呼び出しがないことは決定的テストで確認する。実際の使用量は同じfixture条件で測定し、cold/warmや経路を区別する。レビュー修正の品質を落として節約する目標や、未測定の何％削減という目標は置かない。

## 実装手順と受け入れ確認

各工程は前提を確認してから次に進み、実際に行った確認と結果を短く記録する。不一致は条件を弱めず修正する。同じ失敗に新しい根拠が増えない場合は、その工程と依存部分だけを設計再検討に戻し、独立に進められる工程は続ける。

### P0 — 両方の通常タスクで一度限りの親出力を安全に回収できるか

- 出発点：`ThreadManager.send/get`、端末の `sendMessage/conversation` とhook。既存コードにプリセット用出力schemaはない。
- まずfake runtime／fake端末ログで受理ID、対応ターン、最終回答、重複イベント、遅延ログ、割り込み、無関係なJSONを検証する。その後、隔離した小さなfixtureで実モデルを使い、親の通常文脈から契約を1回作れるか確認する。
- 実モデルはworkspace指示どおり、GPTは **`gpt-6-luna` / `low`**、Claude Codeは **`haiku` / `low`** を明示する。利用できなければ勝手に別モデルを使わず未検証と記録する。UIデフォルトモデルを変更しない。
- 通過条件：正常な該当ターンからのみ契約を一度取得し、無関係な出力・中断ではworkerを0回起動し、重複再送・完了イベントでは追加起動を0回にする。プロンプト作成がソースや親のモデル・ツール設定を変更しない。
- ログ確定が遅い場合はイベント後の限定的な再読込を実装範囲とする。対応ターンを確実に照合できない経路では、取得済みブリーフの手動確認でのみ開始可能とし、自動起動は有効にしない。通常端末と同じ会話を別headlessプロセスで同時再開する回避策は採らない。仕様を満たせない場合は自動起動部分を設計再検討する。

### P1 — 設定・UI入口とrunの永続化

- P0で確認したプロトコルに合わせ、`settings.js`、`types.ts`、モデル設定、`OpenInMenu` の任意task参照、認証済みRPCとrun保存を追加する。既存の共通メニュー利用箇所はtask未指定で後方互換に保つ。
- 通過条件：役割別モデル／推論が再起動・別ブラウザで保持され、旧設定は空で読める。未設定・非表示・利用不可・非対応の値は起動前に拒否し、課金経路は切り替わらない。通常dsh／通常端末だけに項目が表示され、スマホ幅とキーボードで開始・取消ができる。クリックだけで未保存の別モデルが起動しない。
- この段階で書き込みを有効にする前に、次工程の排他を必須とする。

### P2 — 専用workerの起動・排他・停止

- `AbRunner` と `ClaudeRunner` の既存パターンを参照し、小さなプリセット実行アダプターを作る。`runtimeKey`、dsh patch、MCP割当でプリセット所有runを区別する。ABの状態・権限は変えない。
- `guardExecution`／各起動入口へ今回のrunを接続し、予約・開始・検証までの競合を防ぐ。端末のraw inputやdshの自動継続にも抜け道がないか確認する。
- 通過条件：親は元のモデルとsessionのまま、指定したworkerが1つだけ開始する。契約だけを渡し、常設委託MCP・孫委託・goalは付かない。両方向・親子フォルダー・開始競争で二重writerを拒否する。全停止・source削除・再起動後に勝手に再開せず、遅延イベントでも次工程を開始しない。Claude Codeの認証・権限の同意を維持する。

### P3 — 実装／レビュー修正の完遂と証拠

- `Checkpoints.snapshot/reviewDiff`、`sourceSnapshot`、`ExecutionVerifier.verify` を利用し、eco固有の親判定プロンプトを移植しない。Git ref指定と旧端末のファイルレビューを追加し、2つの基準点を保存する。
- fixtureに、実装者がコミット済みのバグ、staged/unstaged/untracked/deleted、作業前からの変更、複数ターン、非Git、差分不明・除外対象を用意する。最初の実装を見落とさず、レビュワーの修正差分だけも取り出せることを確認する。
- fake workerが「問題を見つけた」と報告だけして終了したケースはcompletedにせず同じworkerへ継続する。実バグfixtureでは指摘→修正→回帰テスト成功まで確認し、未修正・失敗・中断・確認不能を成功扱いにしない。問題なしなら無関係な変更をしない。自動継続が同一失敗で進捗なく回り続けないことも確認する。
- モデルに何を渡したかをテストし、親の推論・実装者の完了宣言をレビュー初期入力に混ぜない。親へ結果を表示するだけではモデルを呼ばず、明示的な「結果を渡す」のみ追加送信する。
- UIの動作確認が必要なfixtureは明示的なブラウザ有効化で確認し、無効時に未確認を隠さない。大きいログや差分の省略は全文参照と範囲を示す。検証中／後の外部編集で証拠を古いと判定する。

### P4 — 回帰・使用量・文書

- 新規テストに加え、下記の既存48件、設定・通常タスク送信・端末送信・排他に関連するテストを実行する。新規テストの命名は既存の `node --test` に合わせる。
- `npm run typecheck`、`npm run build`、必要な全体 `npm test` を実行する。これらのscriptは調査時のpackage.jsonに存在する。Nodeの前提は同ファイルのenginesに従う。
- 実モデル確認はP0と同じ指定のみ。usageの取得不能と0を分け、未使用時の追加モデル入力なし／履歴非複製／親の不要な再起動なしを確認する。節約率は測定できた比較条件を伴ってのみ報告する。
- 実装が動作した時点でfeatures/usage等の利用者向け説明とCHANGELOGを更新し、本書は調査・判断の記録へ位置付ける。常設サブエージェントとUIプリセット、報告専用レビューとレビュー修正を混同させない。
