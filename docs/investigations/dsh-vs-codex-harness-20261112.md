# dsh と Codex CLI のハーネス比較（2026-11-12）

[← GPT消費の見直し](../gpt-efficiency.md)

dsh（0.2.2-rc.1、PTCオン）と、同梱の Codex 0.167.0（GPタスク）が、モデルに実際に何を送り、モデルがどう道具を使ったかを、保存済みのログから比べた記録です。新しい実行はしておらず、利用枠は使っていません。コードは変更していません。

- dsh のログ：`dsh-home/sessions/…/session.v4.jsonl.zstd`（`system/message`、`request/header`、`tool/call`、`tool/ptc-dispatch-start`、`assistant/message` の `usage`）
- Codex のログ：`codex-home/sessions/<日付>/rollout-*.jsonl`（`session_meta.base_instructions`、`additional_tools`、`custom_tool_call`、`token_usage_record`）

## 送っている内容の違い

| | dsh（PTCオン） | Codex 0.167.0（GPT-6系） |
| --- | --- | --- |
| モデルが直接呼ぶ道具 | `run_code` の1つ | `exec`、`wait`、質問、サブエージェント系 |
| プログラムの渡し方 | JSON の `code` 文字列 | 生の JavaScript（JSON で包まない custom ツール） |
| プログラムから呼ぶ道具 | `read`・`edit`・`write`・`grep`・`glob`・`pwsh`・ジョブ・todo・MCP など | `exec_command`（シェル）・`apply_patch`・`write_stdin`・`view_image`・Web・MCP |
| 基本の指示 | 28,330 文字（道具の型宣言を含む） | 17,793 文字（人格・報告の書き方・許可の取り方が大半） |
| 道具の宣言 | `run_code` 3,215 文字（型宣言は上の指示の中） | 36,045 文字 |
| 出力の上限 | 道具ごとの既定 | 呼び出しごとにモデルが `max_output_tokens` を指定 |

Codex も GPT-6 系では「プログラムを書いて道具を呼ぶ」方式です。dsh の PTC と考え方は同じで、違いは細部にあります。Codex の基本指示のうち作業の進め方は12行ほどで、効率に関わるのは「検索は `rg`」「独立した検索と読み取りは1回の `exec` にまとめる」の2点です。

## 長い作業での道具の使い方

同じ課題ではないため、傾向だけを見ます。

| | リクエスト | プログラム1回あたりの道具呼び出し | 道具の結果（文字数）中央値／9割点 | キャッシュ率 | 1リクエストあたり出力 |
| --- | --- | --- | --- | --- | --- |
| dsh Terra/xhigh（tagame-game、修正） | 53 | 4.28 | 1,530／23,773 | 97.6% | 589 |
| dsh Terra/xhigh（tagame-game、ブラウザ確認） | 61 | 1.63 | 863／11,978 | 96.3% | 131 |
| dsh Terra/xhigh（Agent Desk、機能追加） | 27 | 3.58 | 872／16,887 | 95.1% | 303 |
| Codex Terra/high（tagame-game、修正） | 89 | 1.05 | 486／5,880 | 98.4% | 326 |
| Codex Terra/xhigh（Agent Desk、調査と修正） | 26 | 2.16 | 3,069／30,645 | 95.2% | 243 |
| Codex Luna/xhigh（Agent Desk、リリース作業） | 150 | 1.01 | 1,586／4,524 | 98.7% | 253 |

- **まとめ方:** dsh は1回のプログラムに道具呼び出しを3〜4個入れています。Codex は道具呼び出しは1〜2個ですが、1つのシェルコマンドに `rg` や `Get-Content` を `;` でつないでまとめています。
- **出力の絞り方:** Codex のモデルは呼び出しごとに `max_output_tokens` を 1,000〜6,500 で指定していました。
- **待ち時間:** Codex は長いコマンドの完了を `write_stdin` の空打ちで待ち、89 リクエスト中 32、150 リクエスト中 97 が待つだけのリクエストでした（Windows では1回の待ちが最長30秒）。dsh はジョブとして待つので、ここは dsh が有利です。
- **編集:** Codex は `apply_patch`。dsh は `edit` で、1つの作業で 94 回呼んだ例がありました。

## 取り入れる候補と検証結果

E:\Agent-Desk-Lab（本体とは別のリポジトリ）で、本物の dsh と同梱 Codex に同じ課題を Luna で各4回走らせて測りました。詳しい数値はラボの `lab/RESULTS.md` にあります。課題は、Agent Desk のソースを読んで10問に答える `investigate` と、小さなライブラリに機能を足して隠しテスト20件で採点する `edit` です。

| 課題 | | 費用（API換算） | 時間 | 得点 |
| --- | --- | --- | --- | --- |
| investigate | dsh high ／ Codex high | $0.00788 ／ $0.00485 | 62 秒 ／ 33 秒 | 37 ／ 39（40点中） |
| investigate | dsh max ／ Codex max | $0.00767 ／ $0.00596 | 65 秒 ／ 48 秒 | 40 ／ 40 |
| edit | dsh high ／ Codex high | $0.00514 ／ $0.00564 | 84 秒 ／ 94 秒 | 全回満点 |
| edit | dsh max ／ Codex max | $0.01001 ／ $0.01138 | 231 秒 ／ 204 秒 | 全回満点 |

読み取り中心の課題では Codex が安く速く、編集課題ではほぼ互角でした。読み取りでの差の大部分は、道具の結果の量（dsh 125k 文字、Codex 74k 文字）です。

1. **プログラムを JSON で包まずに渡す：見送り。** 公式の GPT 経路は custom ツールを通しましたが、エスケープの失敗は減りませんでした（JSON 17/20、生の JavaScript 16/20）。失敗は JavaScript の文字列リテラルの層で起きています。本文を `run_code.data` に入れる今の形は 20/20 で正確でした。
2. **呼び出しごとの出力上限：見送り。** 案内文を1行足すだけでは、モデルは丸ごと返す癖を直しませんでした。上限を必須の引数にすると道具の結果は 30〜39% 減りましたが、一覧が途中で切れて正答が下がり（8.9 → 7.8）、時間は約2割延びました。
3. **`apply_patch` を有効にする：見送り。** 品質は全回満点で差がありません。high では引数の形とパッチ文脈の間違いによる往復が増え、費用 +33%、時間 +51% でした。max では差がありませんでした。
4. **戻り値の表示を詰める：見送り。** 道具の結果の 32% が JSON の字下げ・引用符・キーでした。字下げをなくしても、モデルが多く返すので減りません。文字列の配列を1行1項目で表示すると high では費用 −19% でしたが、max では費用 +15%・時間 +34% と悪化しました。
5. **grep パターンの書き方を案内する：採用（`server/ptc-guidance.js`）。** dsh のプログラムの約1割が「grep pattern rejected by ripgrep」で失敗していました。`(` を含むパターンが、JavaScript の文字列でバックスラッシュが消えたまま ripgrep に届くためです。`Promise.all` でまとめていると、同じプログラムの他の結果も失われます。PTC の案内に「正規表現の記号は `[(]` のように角かっこで書く」という1行を足すと、grep の失敗は 55 本中 7 本から 41 本中 0 本になりました。high では費用 −16%、時間 −37% で、得点も上がりました（37 → 39）。max では費用・時間に差がありませんでした。
6. **取り入れないもの：** シェルだけで読む方式（PowerShell の引用が増える）と、`write_stdin` での待ち方。

GPT が Codex の道具の形に合わせて訓練されているかについて、1 と 3 の結果は「形を合わせても良くならない」ことを示しています。
