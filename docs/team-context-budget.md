# 設計記録：子の共通文脈予算

## 背景と採用理由

大きなウィンドウを持つ子は、自動要約に達するまで長い入力を繰り返し処理する。会社名の対象リストでは、新しいモデルや容量変更に対応するたび例外が増える。そこで、TM・ecoのdsh子という役割に共通の要約開始目安を設ける。利用者向けの仕様・対象・適用時期は[子の文脈予算](team.md#子の文脈予算)を正とする。

## 実装

- `server/team-child-compaction.js` が上流の `BasicCompactionEngine` を継承する。値は `CHILD_CONTEXT_BUDGET` にまとめ、実行時に解決されたモデル容量から上流のexact-routeポリシーへ変換する。provider/modelはポリシーの宛先であり、会社名による条件分岐はしない。
- 現行の上流処理は、windowに対する比率と、応答予約・headroomを引いた圧力予算の小さい方で自動要約を判断する。比率を共通予算で上から抑えることで、従来より遅らせずに開始目安を制限する。予約量やモデル容量そのものは変えない。
- 同じプロセスで複数ルートが並行するため、元の設定を保持し、対象ルートだけの派生ポリシーを置き換える。繰り返し再開しても比率をさらに掛け合わせない。容量が変わって共通予算が不要になれば元のポリシーへ戻す。
- 要約後に保持する末尾が新しい目安以上になってしまう場合のみ、末尾を目安の半分へ縮める。それ以外の既存保持設定、要約モデル、再試行、auto設定は維持する。
- 上流の古いツール結果の削減、要約範囲のツール対整合、保存、手動要約、overflow復旧、キャンセルを再実装しない。インストール済みパッケージにも書き込まない。
- 子専用patchで元の要約エントリーを無効化し、子用バックエンドを登録する。patchのnameは改名ではなく照合条件なので、名前の上書きには依存しない。元エントリーに残る設定を元のLoaderスコープで評価して引き継ぐため、auto・モデル別設定・式を既定値で消さない。親・通常タスク・AB・Claude Codeの実行方式は対象外。保存データの形式は追加・変更しない。

## 採らなかった方法

- 特定会社・モデルだけの例外：問題の軸が容量・役割と一致しない。
- 全体や子のwindow容量を小さく偽装：応答上限や他の判断まで変わる可能性がある。
- 独自の監視AIや要約処理：追加のモデル利用と、上流の保存・復旧処理の二重実装を避ける。

## 制約と検証

40万は送信トークン数の厳密なハード上限ではない。要約や要約直後の非キャッシュ入力に費用がかかり、品質を落として再調査が増える可能性もある。実際の節約率やサブスクの残量改善は未検証。

上流の設定構造と `compactIfNeeded` の継承契約に依存する。dsh更新時には `test/team-child-compaction.test.js`、`test/team-child-runtime.test.js`、`test/team-child-compaction-runtime.test.js` を実行する。最後のテストは実際のdsh/ACPローダーとローカル模擬応答を使い、親・子のbackend分離と再起動後の再適用を検査する。実モデルによる品質・課金比較ではない。
