# AB：2社に相談してから実装

[← README に戻る](../README.md)

プロジェクトまたは My PC の **AB**（eco・TMの隣）から始めます。TM・ecoの設定や履歴は変更しません。

## 使い方

1. **相談A・相談B・判断／報告リーダー・実装用モデル**の4枠を選びます。Claude Codeと、接続済みのカタログモデルを選べます。モデルの隣で、4担当それぞれの推論レベルも選べます。未変更・旧設定の未指定値は、新しく始める相談では「中」（`medium`）へ解決し、Claude Codeにも `--effort medium` を明示します。中がない既知モデルでは既存の近傍規則（中より下の最大、なければ上の最小）で選び、その実際の値を表示・保存します。推論指定ができない既知モデルは「指定不可」として無効化します。対応不明なら中を要求し、非対応や適用未確認なら実行時にエラーにします。モデル変更時も対応する近傍値を選びます。保存済みの明示指定は再表示だけでは変更せず、既知の非対応値は「非対応」と表示します。今回使う担当の値が非対応なら、対応値に直すまで開始しません。推論指定不可のモデルに古い値が残っている場合は、メニューの「指定なし」で解除できます。過去の実行・開始済みジョブ・再試行用設定を一括で書き換えることはありません。リーダーの推論レベルは判断・実装指示・直接実装・レビューで共用します。モデル・推論レベル・スイッチの変更はアプリ側へ保存され、次回や別端末でも使えます。dsh実行時に明示した推論レベルが非対応と判明した場合は、近い値へ黙って置換せずエラーにします。Claude Codeの選択肢は既存の許容語とカタログに基づきますが、全モデル・CLI版での対応は保証しません。非表示・提供終了・未接続のモデルに自動で代替モデルを割り当てることはありません。
2. 相談文を書いて「2社に相談」を押します。開始・追加相談の両入力欄にスクリーンショットを貼り付けられ、プレビューから削除、画像だけの送信もできます。PCはEnterで送信、Shift＋Enterは改行です。IME変換中のEnterは確定のみ、タッチ端末のEnterは改行です。アップロード中や送信中は再送せず、失敗時は本文と成功済み添付を保持します。アプリが同じ原文と画像をA・Bへ直接送り、別々のセッションで並列に検討させます。最初の振り分けにリーダーは呼びません。
3. 両方の報告が正常に揃うと、原文と両報告をリーダーへ渡します。結論と根拠・異論・未確認事項を確認してください。元の報告はそれぞれ開けます。
4. 必要なら追加条件をリーダーへ送って案を修正します。これはリーダーによる再検討です。初版ではA・Bへの自動再調査や無限の討論ループは行いません。
5. **「この案に同意して実装」**を押した場合だけ実装へ進みます。案が更新された場合、古い案への承認は無効です。相談だけで終えても構いません。
6. 実装完了・レビュー完了・要確認の後もリーダーへ返信できます。元の依頼、承認済み計画、各報告、追加会話を新しい読み取り専用セッションへ渡します。返信だけでは再実装せず、更新案を再承認した場合だけ実装します。追加相談を始めた時点で古い承認・段階再試行は無効です。ユーザー発言と回答は時系列に並びます。

### 画像の扱い

PNG／JPEG／GIF／WebP、1枚10MB以下、相談全体で異なる画像20枚までです。発言との対応を保存し、履歴にも表示します。判断・追加相談・承認後の実装・レビュー・再試行にも画像を渡します。dshにはACP画像ブロック、Claude Codeにはstream-jsonのbase64画像ブロックを送り、画像パスだけを渡して読み取りに任せる方式ではありません。

画像付きABはClaude Code、Claude API、ChatGPTのモデルを対象とします。その他の経路は画像を捨てず明示的に拒否します。全モデル・CLI版での画像読解成功を保証するものではなく、認証切れやモデル側のエラーはそのまま報告します。画像送信やEnter送信は実装承認ではありません。

## 実装の切り替え

- **実装用モデルに委託：ON** — リーダーが承認済みの案から、設計・制約・変更範囲・完了条件・検証方法をまとめた指示文を作ります。実装用モデルには元の依頼・最新版として承認された計画・生成した実装指示を区別して渡します。相談履歴全体は渡しません。承認済み計画が明示的に更新した条件は古い条件より優先し、更新されていない元依頼の制約は維持します。実装指示だけで範囲を広げず、解消できない矛盾は報告させます。
- **OFF** — 承認済みの案を渡して、リーダーと同じモデルで直接実装します。
- **委託後にリーダーがレビュー：ON** — 実装報告をリーダーへ渡し、承認済みの案・実際のコード・報告された検証結果を照合させます。
- **OFF** — 実装用モデルの報告をそのまま表示し、リーダーは呼びません。「リーダーレビュー未実施」と表示します。

実装担当は承認時にも切り替えられます。リーダー直接実装の場合、委託後レビューのスイッチは適用しません。どちらの場合も実装担当にはテスト等の検証を求めます。レビューOFFは検証を省く意味ではありません。

段階ごとに新しいセッションを使い、その段階に必要な文脈を明示的に渡します。直接実装も、相談時の読み取り専用セッションを権限昇格させず、同じリーダーモデルの実装セッションで行います。

実装担当（dsh）は常にフルアクセス（サンドボックスなし）で動かします。作業フォルダのWindows権限設定に依存しないため、サンドボックス準備エラーで止まりません。相談・判断・指示作成・レビューは読み取り専用のままで、実装担当の委託・無人ゴールも禁止です。Claude Codeの実装は従来どおり `bypassPermissions` で動作します。

## 相談モデルのツールを絞る

設定はA・Bと読み取り専用のリーダー段階に共通です。

| 設定 | 調査に使えるツール |
|---|---|
| ON（初期値） | ファイルの読み取り・検索 |
| OFF | 上記に加え、Web検索・ページ取得 |

不要なツールは定義から外します。**OFFでも編集・シェル実行・ブラウザ操作・デスクトップ操作・画像生成・サブエージェントは渡しません。** ブラウザや外部MCPで読み取り専用制限を迂回できないようにするため、TMの「子のツールを絞る」と除外対象は完全には同じではありません。Web検索の利用可否は接続済みサービスにも依存します。

dshは専用の読み取り専用ランタイムと実行時の許可リスト、Claude Codeは `Read,Glob,Grep`（OFFなら `WebSearch,WebFetch` も追加）とMCP無効化で制限します。AB内部の担当タスクを通常のタスクRPCから操作して、権限を変更したり別の実装指示を送ったりすることもできません。

## 停止・記録・注意

- 上部の停止ボタンで実行中の担当を停止します。停止要求が完了後に届いても、完成済みの案や報告、承認・追加相談できる状態は保ちます。片方の相談が失敗した場合、もう片方も停止します。停止完了を確認できない間は停止ボタンを残し、再試行・削除を許可しません。中断・失敗した報告を正常な相談結果としてリーダーへ渡しません。
- 承認後の実装指示作成・実装・レビューの失敗や中断、権限不足による「要確認」は、「この段階を再試行」から明示的に再試行できます。相談からやり直さず、元のジョブと同じモデル・推論レベルを使い、元依頼・承認済みの案・前回の入力と結果を渡します。委託実装では生成した実装指示も区別して渡します。保存済みジョブは書き換えず、旧形式のジョブでも再試行時に元依頼と承認済みの案を補います。**変更済みのファイルは戻しません。** 担当には現在の差分を先に確認し、完了済みの外部操作を繰り返さないよう指示します。旧版で「要確認」のまま止まった記録にも、再起動後に再試行を表示します。
- 案の確認待ち、実装報告、レビュー報告、エラーをAB単位で通知します。通知を開くとAB画面へ移動します。
- 無人の担当は承認プロンプトを利用できません。dshの各担当には、相談・判断・指示作成・レビューは読み取り専用、実装は既にフルアクセスであることを明示し、`run_code`・内部ツール・通常ツールの `sandbox_permissions` と `justification` は省略するよう指示します。通常チャット用の固定モデル委託指示も、ABでは委託ツールと一緒に除外します。権限制御や昇格拒否を緩める変更ではありません。権限承認を求めた場合は拒否して先へ進め、実行されなかった操作を報告とレビュー入力に残します。実装で未実行操作があれば、レビュー後も「要確認」と再試行を残します。Windowsの `SetNamedSecurityInfoW failed (Win32 5)` も実際のツール失敗から検出し、承認要求がなくても「要確認」にします。拒否した操作を自動で許可・昇格することはありません。
- アプリ再起動で中断した作業は自動再実行しません。承認待ちの案は残ります。
- サイドバーのAB行の三点メニューから、名前変更・履歴コピー・アーカイブ／復帰・削除を行えます。名前とアーカイブ状態は保存され、アーカイブは実行中の作業を停止しません。コピーには元の依頼・各担当の報告・追加会話を時系列で含めます。
- 削除は確認ダイアログを経て実行中の担当を停止します。ABを削除すると、各担当の保存済み記録も削除します。作業フォルダや実装済みファイルは削除しません。
- ABの状態と設定はアプリデータの `ab/state.json`、Claude Codeの担当記録は `ab-agents/` に保存します。dsh担当の詳細記録は通常のタスク保存先に保持し、サイドバーではABの下にまとめます。
- Claude Codeは通常の認証・課金経路を使い、TMと共通の認証方式ごとの明示確認を利用します。各起動前にも再確認します。API・サブスクリプション間の自動切り替えはしません。
- **モデルの完了報告やレビュー報告は、アプリによる合格保証ではありません。** ecoの自動検証・ソース指紋・自動差し戻しはABにはありません。レビュー段階は読み取り専用のため、テストの再実行はしません。問題点はレビュー報告に残し、初版では修正の自動ループには入りません。
- ABの実装はワークスペースを変更します。別の実装タスクと同じファイルを同時に編集しないでください。ecoが保護している作業フォルダではABの起動も拒否されます。
- 最新のメイン報告末尾のAPI換算額（USD／JPY）は、相談A・Bから判断・指示作成・実装・レビュー・再試行までの累計です。個別報告ではその担当の累計を確認できます。[API換算額の意味と未算定](usage.md)。
- 費用節約はモデルの単価・文脈量・再試行回数によります。固定の節約率や金額上限は保証しません。

## 開発時の確認

- 自動テスト：`node --test test/ab*.test.js test/workflow-effort.test.js`。実際のThreadManagerの承認イベントとdshのツール実行基盤も検証します。
- 入力・推論UIの分離検証：`node test/fixtures/serve-ab-ui.mjs` を起動し、表示URLでDevToolsから `await abTest.run()`。開始／追加相談の貼り付け・失敗時保持・Enter／IME／タッチ分岐・二重送信、4担当のメニュー、ecoの保存待ちと実行リクエストを模擬RPCで検証します。狭い画面でも実行できます。IMEとタッチ分岐は合成イベント／ポインター判定の模擬であり、実IME・実スマホの確認とは別です。
- 実Claude Codeの画像読み取り：`node test/fixtures/live-ab-vision.mjs --run`。現在のClaude認証で1回のモデル呼び出しを行う明示的な診断です（利用枠・課金を消費し得ます）。AB経路で色のサンプル画像を送り、読み取り結果を検証します。`npm test` では実行しません。認証切れなどの失敗を成功扱いしません。
- ランタイム起動：`node test/manual/ab-runtime-smoke.mjs`。隔離した一時データで3種類のABランタイム（相談2種類・実装）を起動し、モデルへは送信しません。
- 画面：`npm run build` 後に `node test/manual/ab-ui.mjs`。表示されたURLを開きます。応答は全て模擬です。環境変数 `AB_FIXTURE_FAIL_ONCE=1` で最初の実装を失敗、`AB_FIXTURE_DENIALS=1` で未実行操作を報告させられます。確認後は同じURLの `/fixture/shutdown` にアクセスして終了します。
