# エコモード（eco）

[← README に戻る](../README.md)

プロジェクトの **eco**（TMの左）から始めます。既存のTMとは別のモードで、TMの保存済み設定は変更しません。「設定 → エージェントチーム」の方針・プレイブックはTM専用で、ecoには渡しません。共通のカスタム指示は引き続き適用されます。

## 使い方

1. 「親」「子」のモデル名を押し、ABと同じモデルピッカーから直接選びます。子の接続先を別に選ぶ必要はありません。親にはClaude CodeのOpus／Sonnet、またはカタログにあるClaude API／GPTを使えます。子はHaiku級など、用途に合った低価格モデルを選んでください。親・子の実行方式とモデルは選択した時点でアプリ側に保存し、開始せずに閉じた場合や開始に失敗した場合も次回に引き継ぎます。同じアプリに接続するPC・スマホ間でも共通です。従来のブラウザ内だけの選択はアプリ側に未保存の場合に一度移行します。キー削除・非表示・提供終了などで使えないモデルは「モデルを選択」に戻し、再選択するまで開始しません。別のモデルや課金経路には自動で切り替えません。
   モデルの隣で親・子の推論レベルを独立に選べます。未変更・旧データの未指定値は、新規開始では親・子とも「中」（`medium`）へ解決し、Claude Codeにも明示指定します。中に非対応の既知モデルでは近傍の対応値を表示・保存し、推論指定不可なら選択欄を「指定不可」として無効化します。対応不明なら中を要求し、dshが非対応・適用未確認を返した場合は送信前にエラーにします。モデル／プロバイダー変更時も近傍の対応値を選びます。保存済みの明示値は再表示だけでは変更せず、既知の非対応値は「非対応」と表示して、対応値に直すまで開始しません。推論指定不可のモデルに古い値が残っている場合は、メニューの「指定なし」で解除できます。推論値もアプリ側に保存し、再表示・再起動後に復元します。API／サブスクリプションモデルはカタログが示す値、Claude Codeは既存のCLI用選択肢を使います。保存中に開始しても最新の選択の保存完了を待ち、親と子のそれぞれの起動へ値を渡します。開始済みecoには遡及しません。
2. プロジェクトの検証コマンドを登録します。例：`npm test`、`npm run build`。ID、実行場所、制限時間を設定できます。
3. 「始める」を押し、親に依頼します。親が完了条件・自分で確認する箇所・使う検証を決めてから、子へ委託します。

```text
親：方針・完了条件
  → 子：調査・実装
  → アプリ：検証・限定的な差し戻し
  → 親：結果と根拠をまとめて判定
```

検証設定はプロジェクトごとに保存します。開始後も、エコモードのパネルにある「検証設定」で変更できます。既に委託した作業は委託時の検証定義を使い、後の設定変更では置き換わりません。親は必要なときだけタスク専用の追加検証も指定できます。

## 実行と判定

- **2段構成：** 親と子の低枠だけを使用します。中位モデルへの自動昇格や、別課金経路への自動切り替えはしません。
- **進め方は親が判断：** 探索・調査・実装は原則として低コストの子へ任せ、親は依頼の解釈・方針と範囲の決定・根拠のレビューに集中します。子の調査をやり直したり細かく往復したりすることは避けますが、判断に必要なコードの確認や既存の条件内での小さな直接修正は禁止しません。調査の深さ、計画の詳しさ、レビューの必要性は依頼に応じて判断し、プリセット・固定工程・レビュー回数制限は追加しません。
- **書き込みは直列：** 実装、検証、親の判定が終わるまで、次の書き込み担当は開始できません。ECOの実装の子を起動・再開するときは、同一・上位・配下のフォルダを対象に、復元中のthread、書き込み可能で `running` の別thread、自身の親以外で作業中のClaude Code端末、未完了のチーム作業を確認して拒否します。一方、別タスクの開始・入力・復元をECO側から制限するガードは、ECOフォルダとその配下だけを対象とし、上位フォルダは対象外です。現状は入口・開始順で判定範囲が異なります。
- **競合時の情報：** 拒否理由に加え、最初に検出した競合タスクの名前・ID、双方の作業フォルダ、競合側が対象の同一／上位／配下のどれか、判定に使った状態を返します。チームの子はチームID・子ID・タスクIDと段階（`working`／`verifying`／`review` など）も示します。フォルダの表記と判定に使う正規化後のパスが異なる場合は両方を示します。子の作業フォルダはチームのフォルダであり、出力先やシェル内の作業場所だけを変えても判定対象は変わりません。状態はアプリの記録であり、`running` の表示だけでは実際に処理が継続しているかまでは確定しません。競合相手を確認し、無関係なタスクの一括停止やガードの無効化は避けてください。
- **子のツール：** ブラウザ・デスクトップ・画像などの追加ツールも常に渡します。`tools: true` の指定は不要で、以前に開始したecoの子も次回のセッション起動から対象です。通常のTMのツール設定は変更しません。
- **調査は並列：** 親は `mode: research` の調査専用の子を起動できます。dshの子は親の権限にかかわらず読み取り専用で、子自身による権限変更・昇格は許しません。起動結果と `status` に調査モードを明示し、子自身のシステム指示にも実際の権限制約を渡します。読み取りだけの `run_code`・内部ツール・通常ツール呼び出しでは `sandbox_permissions` と `justification` を省略します。これらは現在の権限の指定ではなく昇格要求です。Claude Codeの調査専用の子の組み込みツールはRead／Glob／Grepに限定しますが、MCP・ブラウザは利用できます。追加ツールを使う場合も調査にとどめ、外部への変更操作は行わないでください。
- **調査した子に実装を継続依頼：** 関連する実装は原則として同じ子に依頼します。親は調査報告の根拠を確認して `close`（`accept:true` と `reason`）した後、`implement` に子の名前、新しい `title`・実装範囲を含む `task`・`criteria`・`checks` を指定します。子・モデル・会話を保持したままアプリが実装用へ切り替え、変更前の記録を取り直します。調査の完了条件・判定根拠は実装の記録内にも残します。dshは同じセッションを実装用ランタイムで再開し、Claude Codeも同じ会話を再開します。切り替え時に会話を再開できない場合は、黙って新規会話にせず開始を止めます。通常の `send`・`fresh` やタスクの権限変更では調査の子を実装用にできません。実装・検証・判定までの単一担当制限は新規起動と同じです。無関係な作業や別モデルを使う場合は新しい子に分けます。会話の再利用は再調査を減らせますが、キャッシュ命中や節約率は保証しません。
- **アプリが検証：** 子の初回起動・新しい会話・実装への切り替え・終了後の新しい作業の開始時に、その作業で選ばれた検証ID・コマンド・実行場所を子へ渡します。設定変更後も委託時の定義を使い、同じ作業への通常の追加指示では一覧を繰り返しません。子は再現・対象を絞った回帰確認を優先しますが、必要な全体テストは禁止しません。検証未選択の場合は未実行扱いであることを知らせ、子自身の必要な確認は省略させません。子の最終報告を受けて、選ばれたコマンドを順に実行します。コマンド、実行場所、終了コード、時間、ログ、ソースの状態を保存します。WindowsではPowerShell 7（`pwsh`）、その他では`/bin/sh`を使います。
- **差し戻し：** 「失敗時に子へ自動差し戻し」を明示した検証だけが対象です。最大2回（親は0〜2回で指定可能）。同じ失敗の繰り返し、認証・課金・通信系と判別できたエラー、タイムアウト、対象の変更、キャンセルは親へ戻します。失敗の分類はエラー文による判定なので、環境に応じた完全な分類を保証するものではありません。
- **報告：** 依頼・完了条件・親からの追加指示・アプリが取得した変更ファイル一覧と差分抜粋・検証結果・子の報告を一つのレビュー資料にまとめて親へ渡します。通常の短い報告プレビューでは切らず、大きい資料は項目ごとに省略して全文・差分ファイルのパスを添えます。他の子が作業中の間は成功報告を最大30秒だけ集約し、エラー・停止・承認待ちは先に返します。調査専用の子の報告はコマンド検証・差分取得をせず、親が報告の根拠を確認します。調査の子には事実・根拠・不明点を短く報告し、根拠が十分な場合は実装方針・検証案も添えるよう伝えます。案がまだ作れない場合は推測で埋めさせません。待機中に親を呼び続けたり、キャッシュ維持だけの呼び出しをしたりしません。
- **親の報告待ち：** dshの親はTM・eco共通で、子の作業・検証・未配送の報告があるとき、ターン終了後の自動goal roundを待機させます。目標の内容・active状態・残り回数は保持します。現在のターン内での判断や並行作業は止めません。独立した作業を自動継続で進めたいときは親が `wait({waiting:false})`、報告待ちに戻るときは `wait()` を使えます。ただし未配送の報告・承認要求、ユーザーへの質問、全停止が優先されます。受理された新しいユーザー入力だけが質問待ちを解除し、送信の拒否・重複再送・子の報告では解除しません。質問を閉じた場合は未回答であることを親へ通知します。全停止後の再開指示なしの自動再試行と、停止に追い越された未開始の子への送信も防ぎます。通常タスク・子自身の自動継続には適用しません。ランタイム対応を確認できない場合は親の新しいモデル呼び出しを開始せず、エラーにします。詳しくは[チーム](team.md)。
- **判定：** 親が依頼・完了条件と実際の変更を照合して合格にします。バグ修正は原因と修正、UIは実際の画面と操作、テスト変更は検査を弱めていないかを確認します。**検証成功・未実行・調査のいずれも、`close` の `reason` に親が確認した箇所・結果と合格根拠を短く残すことが必須です。** テスト成功だけを合格理由にしないよう親へ指示しますが、アプリが根拠の正しさや実際のレビュー実施を保証するものではありません。検証に失敗した結果や、検証後にソースが変わった結果は合格にできません。検証コマンドを使わない作業は「未実行」とします。中止も理由が必要で、合格とは別に記録します。
- **停止と再起動：** 「全停止」は実行中の子だけでなく検証も止め、自動差し戻しを止めます。再起動で中断された検証を成功扱いにはしません。

GPT向けの関数ツール定義では、未指定の `strict` を `false` として送ります。[Responses APIの自動strict変換](https://developers.openai.com/api/docs/guides/function-calling#strict-mode)で `sandbox_permissions` などの任意引数まで必須扱いになり、読み取り専用調査が不要な昇格要求で止まることを防ぐためです。既存namespace内にも適用し、明示的な `strict: true` と元の引数スキーマは維持します。実行時の引数検証・読み取り専用制約・昇格拒否は変更しません。

## 状態記録の範囲と注意

Gitプロジェクトでは、追跡ファイルとGitで除外されていない未追跡ファイルの内容をハッシュ化します。コミットIDや差分だけの比較ではありません。未追跡ファイルの追加・削除も検出し、検証中に作成して削除したソースも変更として扱います。除外された生成物は対象外ですが、監視情報だけで除外ディレクトリと非除外ファイルを区別できない場合は、安全のため「古い」結果として再確認を求めます。サブモジュールは、そのフォルダを別のプロジェクトとして開いてください。

Git未使用のフォルダも使えます。この場合は `.git`、`node_modules`、`.venv`、`venv`、`__pycache__`、`dist`、`build`、`coverage`、`.cache` のディレクトリを除き、ファイルを記録します。除外ファイル、外部依存、外部サービスの状態まで固定する仕組みではありません。

**レビュー差分**は子の作業を始める直前から検証後までを、アプリのデータフォルダ内にある独立したGitチェックポイントで比較します。ユーザーのリポジトリのインデックスやHEADは変更しません。作業前からあった未コミット変更は差分に含めず、新規・削除・未追跡ファイルや、子が途中でコミットした変更も確認できます。差し戻しや `fresh` では元の基準を保ち、`close` 後に新しい作業を `send` すると基準を取り直します。親の修正とフォーマッタの変更も累積差分に含みます。Git除外・依存物などチェックポイント対象外のファイルは含みません。50MiB超のファイルは差分から除外したパスを警告し、バイナリの内容は別途確認します。Gitが見つからない、保存に失敗した、旧バージョンの作業で開始前の記録がない場合は「差分不明」として親へ返し、変更なしとみなしません。差分だけに頼らず親自身が対象を確認します。

**検証の鮮度**は別に、検証開始時のソース指紋を基準に管理します。検証中はソースの変更を監視し、差分を取得できた場合は取得後にも、合格判定時には必ず内容を再確認します。ファイルの指紋取得には1回につき2分の時間制限を設け、検証コマンドの制限時間とは別に扱います。時間切れや読み取り失敗はエラーとして親に伝え、成功扱いにしません。全停止は検証コマンド前後の指紋読み取りにも反映します。レビュー資料の作成が始まった後は、その処理の終了を待ってから停止を報告します。OSのファイル操作自体が応答しない場合は、時間どおりに中断できないことがあります。複数回確認するため、2分は検証全体の制限ではありません。検証前の外部編集もレビュー差分には含みますが、子・親・検証コマンド・外部編集のどれによる変更かは識別できません。「古い」判定は同時編集の防止や変更元の識別の代わりにはなりません。外部エディタや、アプリの管理外で動くプロセスをOSレベルで禁止する機能ではありません。親には、子の作業中・検証中の編集を禁止し、判定待ちで全ての子が待機中の場合だけ範囲内の小さな修正を許可します。親が編集したら `verify` で再検証し、新しい結果を待って判定します。バックグラウンドの書き込み処理は残さないでください。

**コマンドの終了コードが0でも、依頼が正しく完了したとは限りません。** 必要な検証の選定と仕様の確認は親が行います。検証コマンドはこのPCのユーザー権限で動くため、削除・デプロイ・外部接続などの副作用があるコマンドを無条件に登録しないでください。フォーマッタなど意図的にソースを変える検証だけ、「ソース変更と1回の再検証を許可」（`allowSourceChanges`、初期値オフ）を設定できます。許可した検証の実行中だけ変更が検出され、全コマンドが成功した場合に限り、アプリが1回だけ再検証します。通常の検証や検証間での変更、監視エラーは親へ返します。変更したプロセスの特定はできないため、許可した検証中の外部編集まで区別できる保証はありません。再検証の報告と結果JSONには初回記録への参照・初回と再実行の対象状態が残り、親は変更差分も確認します。親が自分でファイルを直したときは `verify` で子を動かさずに再検証できます。

Claude Codeの認証・課金確認はTMと同じ仕組みを使用します。APIモデルは従量課金です。利用枠の消費や節約率をAPI料金比から断定せず、厳密な金額上限も保証しません。

## 記録と初版の範囲

アプリのデータフォルダ内の `teams/execution/projects.json` に検証設定、`teams/execution/runs/<ID>/` に検証のJSONとログ、レビュー全文 `review.md`、差分全文 `changes.patch` を保存します。差分用のチェックポイントは `teams/execution/reviews/snapshots/` に保存します。`teams.json` に依頼文・追加指示・開始時点の記録、完了条件、判定とレビュー根拠、差し戻し回数、親子のターン数、報告・検証回数を記録します。dshが返した使用量は取得できた範囲で保存し、取得できないものは不明のままです。Claude Codeの子はターン終了時のトークン数と推定費用も記録します。Claude Code CLIの親も会話ログからトークン数とAPI料金換算額を取得します。親の最新回答末尾のAPI換算額（USD／JPY）は親と全担当の累計で、再試行や`fresh`前の取得済み消費も含みます。ターン数は引き続き受信したプロンプトフックに基づきます。[API換算額の集計範囲と未算定](usage.md)。

確認役の子の自動追加、検証候補の自動調査、worktreeによる書き込み並列化、TMとの消費比較画面は初版には含みません。
