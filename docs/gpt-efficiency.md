# GPT消費の見直し（2026-11-05）

## 判断の基準

モデル・プロバイダー・課金経路、保存済みの推論レベル・文脈上限は変えず、同じ品質で完了する仕事に必要のない呼び出しだけを減らす。トークン合計、API単価換算、ChatGPT利用枠・実請求は別の指標として扱う。

## 調査と実測から分かったこと

- 個人指示を残したLunaの試行は、パーソナライズOFFのハーネス比較には使わない。
- 個人指示・口調・AGENTS自動読込を除外したTerra/mediumの成功1ペアでは、両者とも同じ独立209チェックに成功した。Agent Deskは未キャッシュ入力30,896、cache read 56,576、出力1,087。Codexデスクトップ同梱エンジンは20,014、111,616、954だった。GUI同士の比較ではなく、通常の実行コアを用いた小課題の1試行である。
- 保存されたusageを同じStandard API単価で換算すると、総トークンはAgent Deskの方が少ない一方、参考額は約29%多い。ただし、上流のキャッシュ内訳が欠落していた場合は未キャッシュ入力と換算差が過大になり得る。実際の購読枠・追加クレジット差を測った値ではなく、一般的な節約率にも外挿しない。
- Agent Deskの4応答目は入力15,057で、保存usageにcacheReadTokensが無く、集計上は0だった。生のcached_tokensが明示的に0だったか、項目が未報告だったかは区別できない。圧縮・モデル変更・LLM retryは無かったが、送信payloadとツール定義の時系列が残っておらず、アプリ側のprefix変化か上流cache/routingかは断定できない。

[OpenAIのキャッシュ仕様](https://developers.openai.com/api/docs/guides/prompt-caching)は先頭一致と設定の安定性を重視する。一方、[文脈設計の原則](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)や[圧縮と観測マスキングの比較](https://arxiv.org/abs/2508.21433)からも、短縮・要約・PTCが品質や再試行を含め常に有利とは言えない。自動的な文脈削減ではなく、完了した仕事単位で測る。

## 実装した変更

### headlessの未使用タイトル生成を止める

Claude Codeから呼ぶGPTサブエージェントのheadlessレイヤーだけで `session-title-llm` を無効にする。呼出元は本文の結果しか使わないため、タイトルの補助推論は不要。通常タスク・チームのタイトル、選択モデル・推論レベル、結果の受け渡しは変更しない。機能の無効化は設定と実ローダーの検査で確認し、未測定の節約率は掲げない。

### 記録済みの使用量を正しく数える

モデルで行った要約の `compaction/summary` も、通常応答と同じ単価規則でターン・担当パネル・履歴へ含める。置換ユーザーメッセージとモデルを使わない圧縮は加算しない。forkの継承境界より前の応答・要約は、その子の新しい消費として再計上しない。これは消費削減ではなく、取りこぼしと過大表示の修正である。

履歴キャッシュのバージョンは維持し、集計規則の署名だけを更新する。残るログは一度読み直し、最後のフレームだけの要約・継承境界、追記・未完フレーム・再起動も既存の増分経路で扱う。削除済みログの取得済み合計と保存済みの確定換算額は保持し、失われた内訳を推定で補わない。表示規則は[使用量](usage.md)を参照。

## 今回は変更しないもの

- 文脈上限の一律縮小、保存済みeffortの引下げ、PTCや必要なツールの一律無効化、retry上限の一律削減。品質・完了率を含む効果が未確認である。
- 要約への推論レベル自動継承。上流BasicCompactionEngineが直前のprovider/modelだけを引き継ぎeffortを渡さないことはオフライン再現した。しかし継承によりキャッシュが改善しなければ、要約の推論消費だけが増え得る。別の明示的要約モデルも尊重する必要がある。
- 過去のツール宣言を永続固定する変更。上流アダプタには過去のtool-additionを現在のツール定義へ引き直す経路があるが、今回のmissで定義が変わった証拠はない。後着ツール・設定変更を壊す修正はしない。

## PTCの固定費とエラー診断

同一の範囲結合課題をGUIで各1回実行したLuna/xhighの比較では、両者とも独立209チェックに合格したが、Agent Deskは11応答・約139秒、Codex appは5応答・約53秒だった。Agent Deskでは1回の編集コードが構文エラーで実行前に失敗し、長い行の後方の日本語により既存診断が原因箇所を示せなかった。個人指示は統制できておらず、1試行のため一般的な優劣や時間差の全原因は断定しない。

SDKの同一出力型を共有aliasへまとめ、引数説明・型情報・ツール一覧は維持する。削減量はMCP構成に依存し、宣言の短縮率がそのまま課金の削減率になるわけではない。また、Nodeの構文エラーで捨てられていた位置情報を、判別できる場合に短い近傍とともに返す。日本語の後ろにあるエラーも、文字幅を確実に換算できる場合は行・列を示す。タブや絵文字などで列を確定できない場合は誤ったcaretを出さない。抜粋の制御文字と不正なサロゲートは無害化する。元の型除去、サンドボックス、ツール結果の扱いは変えない。診断が構文ミス自体を防いだり、実行時間や消費を削減したりする効果は、別途比較が必要である。

## 新規セッションのMCP起動待ち

単純計算でも遅かった試行には、モデルのターン開始前に約2秒の準備があった。MCP接続だけの隔離比較でも直列待ちを再現したため、設定を無効化せず接続の重なりを増やす。対象は名前空間が独立する標準のchrome・desktop・history・imagegenのみで、未知のサーバーやチーム用サーバーを含む場合は従来の直列順を維持する。全設定の検証と全接続の完了前にAgentを公開せず、失敗時は起動済みFiberの破棄と起動処理の回収を待つ。

モデル向けの通常ツール一覧とPTC宣言は既存の名前順を使う。内部registryの登録イベント順は接続完了順になり得る。接続失敗時には後ろの標準サーバーも起動済みの場合があるため、後始末を実ACP・stdioの試験で確認する。2026-11-05の同一PC・ローカル比較（baseline→candidate→candidate→baseline、各4回のセッション作成）では、4サーバーの準備時間の中央値は直列1,551ms、変更後1,090.5msだった。モデルへのpromptは送っていない。接続高速化は初期化区間だけの改善で、モデル応答を含む作業全体が同じ割合で速くなるとは扱わない。

送受信と本文通知の計測は[既定OFFの診断](gpt-cache-diagnostics.md#遅延の切り分け)に追加する。時間表示の終了点や本文の表示方式は変更せず、残る待ち時間はこの観測で切り分ける。

## 要約・verbosityの通信比較（2026-11-05）

SIWCとLuna/lowを固定し、保存済み算数課題の初回system・user・ツール定義を再構成して、現行設定、`reasoning.summary` のキー省略のみ、`text.verbosity: low` のみを各3回、計9推論HTTPで比較した。順序位置はラテン方格で均等化し、送信直前に入力・指示・ツールの一致と変更フィールドを検査した。通常の設定と製品コードは変更していない。

SDK呼出から応答処理終了までの中央値は、現行3.587秒、要約指定省略4.005秒、verbosity低3.534秒。要約省略による数秒の短縮は観測されず、verbosity低との差約53msも安定した改善の根拠とはしない。全9件が期待した「数字だけの回答」との厳密一致チェックに不一致で、baselineも含め品質合格には扱わない。算式からBigIntで期待値を独立再計算して基準は照合したが、回答本文を保存しておらず、数値自体の誤りと書式違反を事後に分離できない。両候補とも本番には採用しない。

生cacheは現行とverbosity低で各1回0、要約指定省略では全回12,032だった。参考額の差を設定の節約効果とは解釈しない。計9回のAPI換算は約$0.00337で、実クレジットではない。全件で生usageの推論トークンは明示0だったため、要約が発生する応答での効果までは検証できていない。各3回、他モデルの同時稼働、キャッシュの偏りが残る単一応答の通信比較であり、MCP起動やUI表示を含む過去のxhigh GUI結果には直接比較しない。

## 残る計測上の制約

上流がusageを記録しないタイトル・検索補助の消費はログ走査だけでは復元できない。現在は[既定OFFのキャッシュ診断](gpt-cache-diagnostics.md)で、実送信内容の変化と生usageの有無を、本文や認証情報を保存せず観測できる。新しい比較でアプリ側の実際の差分が確認されてから、狭い修正を検討する。過去の単発missの原因確定や、実際の節約率の実証はまだ行っていない。
